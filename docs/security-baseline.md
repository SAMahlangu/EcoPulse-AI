# EcoPulse security baseline

EcoPulse has useful application controls, including server-verified Supabase sessions, role checks, private incident media, database row policies, and limits on several costly actions. This checklist records the extra protections needed before real people rely on a public deployment. A code change alone cannot certify a system for a president or other high-risk user; the hosting account, Supabase project, devices, and operating procedures matter too.

## Do these first

1. **Replace the credentials that were shared in the support conversation.** Treat the backend Supabase service key, database password, and Gemini key as exposed. Create the replacement Supabase secret key, set it as backend-only `SUPABASE_SECRET_KEY`, then test administrator invitations and private photo upload before disabling the exposed legacy key in Supabase. Rotate the database password and Gemini key separately, update the backend secret store, restart, and confirm all three integrations. Do not paste replacements into chat, tickets, source files, or frontend `VITE_` variables. Supabase's replacement secret key must be sent in the `apikey` header, not as a bearer token; the code now handles both current and legacy formats during this transition. The public publishable key may be bundled, but only with correct row-level policies.
2. **Protect administrator accounts.** Require multi-factor authentication for every administrator and municipal staff account. Give each person an individual account, remove unused accounts, and never share an administrator login.
3. **Use HTTPS for both the website and API.** Set `APP_PUBLIC_URL` to the final HTTPS website URL and set `CORS_ORIGINS` to only the exact website origins that need access. Configure Supabase Auth's site URL and redirect allowlist to the same production website; remove localhost entries from production settings.
   Release frontend builds now stop unless `VITE_API_URL` and `VITE_SUPABASE_URL` are set to HTTPS addresses. The build emits a Content Security Policy tied to those exact service origins and the map/font services used by the app.
   Supabase is phasing out the legacy `anon` and `service_role` keys by the end of 2026. The frontend and backend now prefer `VITE_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_PUBLISHABLE_KEY`, and `SUPABASE_SECRET_KEY` while temporarily accepting the legacy variable names.
4. **Keep local demo mode off.** `ECOPULSE_LOCAL_DEMO` now defaults to `false` in the sample environment. Do not turn it on in a public deployment. Local password registration also checks that the configured site and request host are loopback addresses, so a reverse proxy cannot make a public site look local by itself.
5. **Put a managed web firewall and shared rate limits in front of the API.** The in-process sign-in, contact, and image-analysis limits help one backend process, but they do not coordinate across multiple workers or servers. Configure provider-level limits for login, password recovery, registration, contact, incident submission, AI analysis, and uploads; alert on repeated failures and traffic spikes.

## Before opening the service to real users

- Confirm every exposed Supabase table has Row Level Security enabled and policies only expose the rows needed by that user. Test as anonymous, resident, municipal, administrator, and suspended user. A service-role key bypasses those policies, so keep it backend-only and use it only after the backend has checked the caller's role.
- Keep incident photos in a private Storage bucket. Use short-lived signed links and verify a resident cannot retrieve another resident's report or photo.
- Enable Supabase email verification, strong password rules, MFA for privileged users, and the smallest practical session lifetime. Review account recovery and administrator invitation procedures.
- The production frontend build emits a restrictive Content Security Policy. Configure the hosting provider to send it as an HTTP header too, along with HSTS and the other browser security headers; a separate static website host must be configured independently from the API. Verify the deployed pages and map/photo flows in a browser after enabling the policy.
- **Resolve the administrator session gap before high-profile use.** The current browser saves access and refresh tokens in `localStorage`, and the backend does not require a verified MFA level for administrator or municipal sessions. An XSS flaw could expose those stored tokens. OWASP advises against storing session tokens in browser storage; move privileged sessions behind a backend-for-frontend or `HttpOnly; Secure; SameSite` cookies, add and test an MFA enrollment/challenge flow, and enforce Supabase `aal2` for privileged API calls.
- Use a managed secret store, rotate keys on staff changes, restrict database network access where the hosting plan allows it, and take encrypted backups. Test a restore before relying on backups.
- Enable security/audit logs and alerts for administrator role changes, account suspension/reactivation, invitation creation, failed sign-ins, unusual report access, and database or storage errors. Keep logs free of passwords, access tokens, reset links, and private report content.
- Run dependency vulnerability checks and an independent security assessment before handling sensitive or high-profile users. Establish who receives incident alerts and how to revoke sessions and keys quickly.

## Current scope

The repository can enforce request and authorization rules, but it cannot verify the live Supabase dashboard configuration, production TLS, firewall rules, backups, administrator MFA, device security, or incident response. Those must be checked in the deployment accounts after the hosting provider is known. This baseline follows OWASP's application verification guidance and Supabase's rules for server-only secret keys and row-level security.
